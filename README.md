# Краулер контактных данных — вариант 1

Многопоточное MVC-приложение на Java 17 и Spring Boot. Принимает стартовые URL, обходит HTML-страницы, извлекает телефоны, email, почтовые адреса и названия организаций. Задания, результаты, найденные ссылки и расписания сохраняются в файловой H2. Дополнительно каждый завершённый обход сохраняется в независимый JSON-файл, а отдельный демон-поток записывает журнал событий. Отдельная СУБД, ключи API и внешние сервисы для проверки не нужны. Каталоги данных создаются автоматически.

## 1. Запуск

Требуется **JDK 17 или новее**. В IDE откройте `pom.xml` как Maven-проект, дождитесь загрузки зависимостей и нажмите Run у `CrawlerApplication.main()`. Предварительно задайте JDK проекта, если IDE его ещё не выбрала.

Либо из корня проекта в PowerShell:

```powershell
.\mvnw.cmd spring-boot:run
```

Linux / macOS:

```bash
sh mvnw spring-boot:run
```

Maven Wrapper сам загружает Maven 3.9.11. При первой сборке нужен интернет для загрузки Maven и зависимостей. Если команда `java` не найдена, установите JDK и укажите его каталог в `JAVA_HOME`.

Откройте <http://localhost:8080/>. Порт по умолчанию — 8080. Все команды ниже выполняются **в другом терминале**, пока приложение работает.

## 2. Быстрая проверка без внешнего интернета

Запуск обхода встроенного сайта:

```http
POST http://localhost:8080/api/crawls/demo
```

Тело запроса не требуется. Ответ: **202 Accepted**, заголовок `Location` и JSON задания с `id`, `status`, `startUrls`, лимитами и счётчиками. Скопируйте `id` для дальнейших запросов.

Полный сценарий PowerShell, включая ожидание результата:

```powershell
$job = Invoke-RestMethod -Method Post -Uri 'http://localhost:8080/api/crawls/demo'
do {
    Start-Sleep -Milliseconds 300
    $state = Invoke-RestMethod -Uri "http://localhost:8080/api/crawls/$($job.id)"
} while ($state.status -eq 'RUNNING')
$state
Invoke-RestMethod -Uri "http://localhost:8080/answer?jobId=$($job.id)&sort=type&direction=asc&size=100" |
    ConvertTo-Json -Depth 6
```

Ожидаемый результат: `COMPLETED`, **3 обработанные страницы и 7 уникальных контактов**:

- Email: `info@vector.example`, `sales@vector.example`, `hr@vector.example`.
- Телефоны: `+74951234567`, `+78125551020`.
- Адрес: `101000, Москва, ул. Примерная, 1`.
- Организация: `ООО Вектор`.

Встроенный сайт содержит относительные ссылки, цикл и дублирующую ссылку с фрагментом `#map`; повторного обхода нормализованного URL не происходит.

## 3. Обход произвольного сайта

```http
POST http://localhost:8080/api/crawls
Content-Type: application/json

{
  "startUrls": ["http://localhost:8080/demo/company/"],
  "maxDepth": 2,
  "maxPages": 30
}
```

Замените `startUrls` на адреса организаций, которые хотите проверить. Можно передать от 1 до 20 HTTP(S)-адресов. `maxDepth`: 0–5, по умолчанию 2; стартовая страница имеет глубину 0. `maxPages`: 1–200 **на всё задание**, по умолчанию 30; лимит должен вмещать все различные стартовые URL. Эти два поля можно не указывать.

Пример PowerShell:

```powershell
$body = @{
    startUrls = @('http://localhost:8080/demo/company/')
    maxDepth = 2
    maxPages = 30
} | ConvertTo-Json
$job = Invoke-RestMethod -Method Post -Uri 'http://localhost:8080/api/crawls' `
    -ContentType 'application/json' -Body $body
$job
```

Во всех следующих URL заменяйте `JOB_ID` на UUID из ответа:

```http
GET http://localhost:8080/api/crawls/JOB_ID
GET http://localhost:8080/api/crawls/JOB_ID/pages
GET http://localhost:8080/answer?jobId=JOB_ID
GET http://localhost:8080/api/crawls/JOB_ID/file
```

Первый запрос возвращает статус и прогресс; второй — страницы, глубину, ошибки и все найденные HTTP(S)-ссылки, включая ссылки на внешние сайты. Третий — сохранённые контакты из H2. Четвёртый читает готовый JSON-снимок непосредственно из файла, без обращения к H2. Получать контакты из H2 можно и во время обхода: уже сохранённые записи доступны сразу. JSON-снимок появляется при завершении задания.

Статусы: `RUNNING` — выполняется; `COMPLETED` — все запланированные страницы обработаны без ошибок; `PARTIAL` — есть успешные и неуспешные страницы; `FAILED` — все страницы завершились ошибкой либо возникла ошибка задания, в том числе сохранения JSON; `INTERRUPTED` — работа прервана завершением приложения. Достижение лимита глубины/страниц является нормальным завершением; `COMPLETED` не означает, что просмотрен весь сайт. Незавершённые задания после перезапуска получают `INTERRUPTED`; найденные контакты сохраняются.

## 4. Получение, фильтрация и сортировка результатов

```http
GET http://localhost:8080/answer?jobId=JOB_ID&type=EMAIL&query=vector&sort=value&direction=asc&page=0&size=10
```

Альтернативный адрес с теми же параметрами: `GET http://localhost:8080/api/contacts`.

| Параметр | Значение |
|---|---|
| `jobId` | UUID задания; без него — контакты всех заданий |
| `type` | `EMAIL`, `PHONE`, `ADDRESS`, `ORGANIZATION`; без него — все типы |
| `query` | Подстрока в значении контакта, без учёта регистра |
| `sort` | `value` (по умолчанию), `type`, `sourceUrl`, `foundAt`, `id` |
| `direction` | `asc` (по умолчанию) или `desc` |
| `page` | Номер страницы, начиная с 0 |
| `size` | 1–200, по умолчанию 20 |

Ответ содержит `items`, `total`, `page`, `size`, `totalPages`. У каждого контакта есть тип, значение, URL источника, время обнаружения и идентификатор задания. Время передаётся в UTC. Неизвестное задание — 404, некорректный JSON/URL/параметр — 400, занятые слоты заданий — 429: повторите запрос после завершения текущих заданий.

Контакты дедуплицируются по типу и нормализованному значению **внутри задания**. Email приводится к нижнему регистру, из телефонов удаляются разделители. Сохраняется первый найденный источник контакта. Повторный запуск создаёт отдельный набор результатов с новым `jobId`.

## 5. Запуск по расписанию

```http
POST http://localhost:8080/api/schedules
Content-Type: application/json

{
  "crawl": {
    "startUrls": ["http://localhost:8080/demo/company/"],
    "maxDepth": 2,
    "maxPages": 10
  },
  "intervalSeconds": 30
}
```

Ответ: **201 Created** и расписание с `id`. Первый запуск произойдёт в течение примерно 5 секунд, следующие — не раньше указанного интервала после старта предыдущего задания. Допустимый интервал — от 30 секунд до 7 дней. Один экземпляр расписания не запускает перекрывающиеся задания; при занятом пуле запуск повторяется на следующем тике.

```http
GET http://localhost:8080/api/schedules
DELETE http://localhost:8080/api/schedules/SCHEDULE_ID
```

В списке расписаний поле `lastJobId` указывает последнее задание; используйте его для запросов статуса и результатов. Удаление возвращает **204 No Content**, прекращает будущие запуски и оставляет результаты и уже выполняющееся задание. Расписания хранятся в H2 и продолжают работать после перезапуска приложения. Пропущенные интервалы не накапливаются.

Готовые HTTP-запросы для IntelliJ IDEA находятся в `requests.http`.

## 6. Как выполнены требования многопоточности

| Требование | Реализация |
|---|---|
| Spring Boot MVC | REST-контроллеры → сервисы → JPA-репозитории и модели; сервер Spring MVC, исходящие запросы через WebClient |
| Кастомный ExecutorService | `ConcurrencyConfig`: собственные `ThreadPoolExecutor`, имена потоков, ограниченные очереди и отказ при перегрузке |
| Прямое использование Thread и Runnable | `AsyncFileLogger.LogWriter implements Runnable`; создаётся `new Thread(...)`, затем вызывается `Thread.start()` |
| Демон-поток логирования | `crawler-log-writer` с `setDaemon(true)` пишет JSON Lines в `data/logs/crawler-events.jsonl`; каждая запись содержит имя потока и `daemon: true` |
| Блокирующие структуры и примитивы синхронизации | `ArrayBlockingQueue`, `SynchronousQueue`, `BlockingQueue.put/take`, `synchronized`; при заполнении очереди журналирования производители ожидают свободного места |
| Конкурентный обход | До 2 заданий и 8 загрузчиков страниц; обход в ширину по уровням; лимит не превышается при конкурентной загрузке |
| Отсутствие ожидания внутри пула загрузчиков | Координаторы ожидают `Future` в отдельном пуле; загрузчики только получают и разбирают страницы |
| Планировщик | `@EnableScheduling` и `@Scheduled` в `ScheduleService`, настройки расписаний в H2 |
| Потокобезопасные структуры | `ConcurrentHashMap.newKeySet()` для посещённых URL и контактов, `ConcurrentHashMap` для robots и ограничителей запросов, `AtomicBoolean` для готовности |
| H2 | Файловая БД `data/contacts.mv.db`, JPA; все таблицы создаются автоматически |
| Собственное файловое хранилище | `FileResultStore`: отдельный `data/results/JOB_ID.json` со статусом, контактами и страницами; чтение через `/api/crawls/JOB_ID/file` не зависит от H2 |
| parallelStream API | `ResultService`: снимок данных из H2 → параллельная фильтрация и сортировка → пагинация; обращения к JPA не выполняются в потоках stream |
| Веб-взаимодействие | Spring WebFlux `WebClient`: таймаут, ограничение размера ответа, ручная проверка редиректов |
| Устойчивость | Ошибка отдельной страницы не останавливает остальные; сохраняются ошибки; пулы завершаются при остановке приложения |

Соответствие таблице оценивания:

| Критерий | Максимум | Где проверить |
|---|---:|---|
| Рабочий Spring Boot сервис с unit-тестами | 6 | `CrawlerApplication`, `ContactExtractorTest`, `AsyncFileLoggerTest`, `FileResultStoreTest`; команда `mvnw.cmd test` |
| Использование простых Thread / Runnable | 10 | `AsyncFileLogger`: отдельный класс `LogWriter implements Runnable`, ручное создание и запуск потока |
| ExecutorService, scheduler, блокирующие структуры, синхронизация, собственный файл, демон-потоки для логирования | 10 | `ConcurrencyConfig`, `ScheduleService`, `AsyncFileLogger`, `FileResultStore`; JSON-снимок и журнал после демонстрационного обхода |
| ExecutorService, scheduler, блокирующие структуры, синхронизация, H2 и фильтрация Parallel Stream | 14 | Те же пулы и планировщик, H2-репозитории, `ResultService.find()` с `parallelStream()`; запросы `/answer` с фильтрами |

`AsyncFileLogger` использует ограниченную очередь событий и единственный поток, владеющий файлом журнала. Загрузчики и координаторы кладут события в очередь, демон-поток забирает их блокирующим `take()` и записывает UTF-8 JSON Lines. При штатной остановке приложение сначала завершает задания, затем запрещает новые события, помещает завершающий маркер после принятых событий и ожидает демон-поток через `join` до 5 секунд. Синхронизация публикации и остановки не позволяет принять событие после завершающего маркера.

Адреса извлекаются из HTML `<address>`, microdata `itemprop` и JSON-LD `PostalAddress`; названия — из microdata организаций и JSON-LD. Email и телефоны также извлекаются из видимого текста и `mailto:`/`tel:`. HTML разбирает Jsoup, JSON-LD — Jackson.

Обход остаётся в пределах **origin** стартовых URL (схема, хост, порт). Ссылки на другие сайты сохраняются, но не посещаются; если нужен другой origin, явно добавьте его в `startUrls`. Фрагменты URL удаляются, относительные ссылки разрешаются, query-параметры сохраняются. Проверяются `robots.txt` и редиректы; `robots.txt` с 404/410 разрешает обход, остальные ошибки запрещают его. Редирект самого `robots.txt` консервативно запрещает обход. Учитываются `Allow`/`Disallow`, специфичные группы User-Agent и `Crawl-delay` через crawler-commons. При `Crawl-delay` больше 10 секунд страница пропускается с ошибкой. User-Agent: `ContactCrawler/1.0`.

Без настроек: задержка между началами запросов к одному origin 200 мс (общая для заданий), таймаут запроса 10 секунд, тело ответа до 2 МиБ, максимум 5 редиректов. Изменить эти значения можно в `src/main/resources/application.yml`.

Приложение читает HTML, полученный по HTTP, и не исполняет JavaScript. Поэтому динамические каталоги с CAPTCHA, авторизацией или блокировкой роботов могут не отдавать контакты. Демонстрационный сайт позволяет проверить всю логику независимо от таких ограничений. Regex телефонов может давать ложные совпадения с длинными числами; адреса без семантической разметки не распознаются. Это учебный сервис для локального запуска, без авторизации; используйте только открытые данные и разрешённые источники.

## 7. Хранилище и тестирование

Консоль: <http://localhost:8080/h2-console>.

- JDBC URL: `jdbc:h2:file:./data/contacts`.
- User: `sa`.
- Password: пустой.

Данные остаются после перезапуска, если запускать приложение из того же рабочего каталога. Контакты можно проверить SQL-запросом `SELECT * FROM CONTACT;`. Также сохраняются таблицы `CRAWL_JOB`, `CRAWLED_PAGE`, `CRAWL_SCHEDULE` и таблицы коллекций URL/ссылок.

Независимое файловое хранилище: `data/results/JOB_ID.json`. В файле есть `formatVersion`, `job`, `contacts`, `pages`. Сначала создаётся временный файл, затем он перемещается на место готового снимка, с атомарной заменой, если её поддерживает файловая система. Окончательный статус задания в H2 публикуется после сохранения JSON. Если запись не удалась, задание получает `FAILED` с пояснением в `error`, а уже сохранённые контакты остаются в H2. Запрос `/api/crawls/JOB_ID/file` возвращает 404, если снимок отсутствует, например пока задание выполняется.

Проверка файла после демонстрационного сценария из раздела 2:

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/crawls/$($job.id)/file" |
    ConvertTo-Json -Depth 10
Get-Content -LiteralPath ".\data\results\$($job.id).json" -Raw -Encoding UTF8
```

Журнал демон-потока: `data/logs/crawler-events.jsonl`. Каждая строка — отдельный JSON-объект с полями `timestamp`, `jobId`, `event`, `message`, `producerThread`, `writerThread`, `daemon`. Для событий `PAGE_LOADED` производителем будет `crawler-page-*`, для событий заданий — `crawler-job-*`. Запись выполняет `crawler-log-writer`, поле `daemon` равно `true`.

```powershell
Get-Content -LiteralPath '.\data\logs\crawler-events.jsonl' -Encoding UTF8 |
    Select-String -SimpleMatch $job.id
```

События: `JOB_STARTED`, `PAGE_LOADED`, `PAGE_FAILED`, `RESULTS_SAVED`, `FILE_SAVE_FAILED`, `JOB_FINISHED`. Записи появляются асинхронно вскоре после события; при перезапуске журнал дополняется. Обычные сообщения Spring и краулера также выводятся в консоль. Пути хранилища/журнала и размер очереди задаются в `application.yml` и имеют готовые значения по умолчанию.

Запуск тестов:

```powershell
.\mvnw.cmd test
```

Тесты используют отдельную H2 в памяти и локальный HTTP-сервер: проверяют извлечение и нормализацию, действительную одновременную загрузку, циклы и дубли ссылок, лимиты, robots.txt, ошибки HTTP, редиректы, размер ответа, фильтрацию/сортировку/пагинацию, валидацию, расписание и встроенный демонстрационный сценарий. Дополнительно проверяются чтение JSON после повторного открытия хранилища без БД, сохранность предыдущего снимка при ошибке сериализации, статус задания при ошибке записи файла, конкурентная отправка 200 событий в небольшую очередь, фактический daemon-флаг писателя, дописывание журнала после перезапуска и завершение с дописыванием очереди. Тестовые файлы помещаются во временные каталоги и `target/test-artifacts`, рабочий каталог `data` не используется. Внешние сайты при тестировании не вызываются.

Сборка и запуск исполняемого JAR:

```powershell
.\mvnw.cmd clean package
java -jar target/contact-crawler-1.0.0.jar
```

В Linux/macOS замените `.\mvnw.cmd` на `sh mvnw`.

Документация используемых механизмов: [Spring WebClient](https://docs.spring.io/spring-framework/reference/web/webflux-webclient.html), [Spring Scheduling](https://docs.spring.io/spring-framework/reference/integration/scheduling.html), [Maven Wrapper](https://maven.apache.org/tools/mavenwrapper.html).
